Switched claude-opus-5 to claude-opus-5-5 and got a 400? Check thinking, tool_choice and computer use first

If you changed the model name from claude-opus-5 to claude-opus-5-5 and the request now fails with a 400, check three things first: whether the request sets thinking to disabled or enabled with budget_tokens, whether tool_choice is any or tool, and whether you declare the computer_20251124 computer use tool. Anthropic's Claude Opus 5 page now marks the model as legacy, and the official Claude Opus 5.5 migration guide has a dedicated section for moving from Claude Opus 5. This page walks through each 400 error message from that guide, the code change, the response changes that do not raise an error, and how to confirm the migration works.

Why does a working claude-opus-5 request return 400 on claude-opus-5-5?

Anthropic's Claude Opus 5 model page lists the model as Active (legacy): it was released on July 24, 2026, it is still available, and its retirement is not sooner than July 24, 2027. The page suggests considering a move to Claude Opus 5.5. So you can keep calling claude-opus-5 for now. Upgrading is optional, but if you do upgrade, changing only the model name is often not enough.

The migration guide says that for a team on Claude Opus 5, the first group of its checklist is the whole list. The request settings in that group that claude-opus-5-5 rejects with a 400 error are: thinking set to disabled, thinking set to enabled with a manual budget_tokens value, tool_choice of type any or tool, and the computer_20251124 computer use tool on the Claude API and on Claude Models on Google Cloud (Google managed).

The guide also says claude-opus-5-5 rejects temperature, top_p and top_k, and a final prefilled assistant turn. Its checklist files those two items under Claude Opus 4.6 and Claude Opus 4.5 or earlier, so code that already runs on claude-opus-5 normally does not rely on them. If your request still sends any of them, even at default values, remove them as well.

Official sources: Claude Opus 5 overview https://platform.claude.com/docs/en/models/opus-5/overview , Claude Opus 5.5 migration guide https://platform.claude.com/docs/en/models/opus-5-5/migration-guide , model deprecations https://platform.claude.com/docs/en/about-claude/model-deprecations .

"thinking.type.disabled" is not supported for this model: remove thinking and set effort

Claude Opus 5 accepts thinking: {"type": "disabled"}. On Claude Opus 5.5, adaptive thinking is always on, and the API returns a 400 with "thinking.type.disabled" is not supported for this model. or "thinking.type.enabled" is not supported for this model. when the request disables thinking or sets a budget_tokens value.

The fix from the guide: send no thinking field, or send thinking: {"type": "adaptive"}, which is equivalent. Control how much the model thinks with output_config.effort, the only request parameter that controls thinking depth on this model. All five levels are supported: low, medium, high, xhigh and max. Where you disabled thinking to save tokens, pick a lower effort; the official before-and-after example uses effort low.

The default changed too. Claude Opus 5 defaults to effort high, while Claude Opus 5.5 defaults to medium, so a request that omits effort now runs at medium. The guide recommends setting effort explicitly and re-running an effort sweep on your own evaluations instead of carrying over a setting tuned for Claude Opus 5.

Revisit max_tokens. It remains a hard limit on total output, thinking plus response text, and thinking tokens are billed as output tokens even when the thinking text is not returned to you. If your code previously disabled thinking, a request can now produce more output tokens. At xhigh or max effort the guide suggests starting max_tokens at 64k.

tool_choice: type "tool" and "any" are not supported: switch to auto with strict tools

On claude-opus-5-5, tool_choice values {"type": "any"} and {"type": "tool", "name": "..."} return a 400 with the message tool_choice: type "tool" and "any" are not supported for this model. The token counting endpoint rejects them as well. Only {"type": "auto"}, the default, and {"type": "none"} are accepted.

The official fix is to use tool_choice auto together with strict tool use or structured outputs, and to say in the prompt when the tool applies. In the guide's example, the tool definition gets strict: true and the user message adds Use the get_weather tool. Because auto lets the model answer without calling a tool, that prompt instruction matters.

Strict tool use accepts only a subset of JSON Schema. Check each tool's input_schema before adding strict: true; every object in the schema must set additionalProperties: false. Official reference: https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use .

does not support tool types: computer_20251124: move to computer_toolset_20260801

On the Claude API and Claude Models on Google Cloud (Google managed), a tools entry of type computer_20251124 returns a 400 with 'claude-opus-5-5' does not support tool types: computer_20251124., followed by the tool types the model accepts.

Declare the toolset instead: send a tools entry of type computer_toolset_20260801 with no name and no display dimensions, and drop the computer-use-2025-11-24 beta header. The agent loop also changes: handle member tool_use blocks, where the action is the block's name rather than input.action; expect several of them in one turn; and echo toolset_name on every tool result. The full list is in the computer use tool documentation under Migrate from computer_20251124: https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool .

On Amazon Bedrock, the guide says computer_20251124 keeps working on Claude Opus 5.5 as it does on Claude Opus 5, so no change is needed there. For other platforms, check the Compatibility section of the computer use tool page.

No 400, but the output looks different: response changes to handle

Responses start with thinking blocks. A response can contain one or more thinking blocks before the first text block. Code that reads content[0].text, or a stream handler that treats the first content_block_start event as text, breaks. Select blocks by their type field and branch on block type in stream handling.

Pass thinking blocks back unchanged. In a tool-use loop, return the assistant message as received, including thinking blocks whose thinking field is empty. The API rejects edited, reordered or partially dropped thinking blocks with a 400. Keep the conversation append-only: for accounts created on or after August 31, 2026, 00:00 UTC, replaying a thinking block after editing the system prompt, tools or earlier messages returns a 400 by default. See Preserved thinking in the official docs if you must change instructions mid-conversation.

Thinking text and progress notes are hidden by default. thinking.display defaults to omitted, so thinking blocks arrive with an empty thinking field. On Claude Opus 5, text written between tool calls came back as text blocks; on Claude Opus 5.5 it comes back as progress-update thinking blocks, at most one before each tool call. No request fails, but an interface that showed that text goes quiet. Set display to summarized, or to updates (beta, header thinking-display-updates-2026-08-18), and render each non-empty thinking block ahead of the tool_use block it precedes.

Refusals and routing. Claude Opus 5.5 can return stop_reason refusal with a stop_details category, and its classifiers cover more categories than Claude Opus 5, such as bio in addition to cyber and reasoning_extraction. Handle that stop reason and configure a fallback. If a router can move a conversation from Claude Opus 5.5 to another model, that model runs without Claude Opus 5.5's thinking blocks; Claude Fable 5.1 and Claude Mythos 5.1 on the Claude API are the exception. In the other direction, Claude Opus 5.5 does read thinking blocks produced by Claude Opus 5.

How to verify the migration worked

Step 1, send a minimal request: model claude-opus-5-5, a max_tokens value, output_config with an explicit effort, no thinking field, no forced tool_choice, no temperature, top_p, top_k or prefill. Success means an HTTP 200 response in which you find the text block by its type, not by position.

Step 2, add your features back one at a time: tools with tool_choice auto and strict: true, the computer_toolset_20260801 toolset if you use computer use, and display summarized or updates if your interface shows progress text. After each addition, confirm the request still returns 200 and that tool inputs match your schema.

Step 3, if a 400 remains, read the error message in the response body and match it to the sections above: thinking.type.disabled or thinking.type.enabled points to the thinking setting, the tool_choice message points to forced tool use, and does not support tool types points to the computer use tool version. The guide also notes that Claude Code can apply the changes with /claude-api migrate this project to claude-opus-5-5; review the result against the checklist afterwards.

Calling through this relay: the platform pricing API lists both claude-opus-5 and claude-opus-5-5 as available, with anthropic and openai endpoint types. For the Anthropic Messages protocol, set the base URL to https://api.openlux.ai without /v1; the client appends /v1/messages. Whether fields such as thinking, tool_choice and output_config pass through the relay unchanged should be confirmed from the actual response, so test with a small request before moving production traffic.
